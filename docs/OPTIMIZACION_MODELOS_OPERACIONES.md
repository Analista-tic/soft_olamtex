# Optimización de Modelos de Operaciones

**Fecha:** 19 de febrero de 2026  
**Estado:** Análisis completo y recomendaciones

---

## 📋 Resumen Ejecutivo

**Enfoque Principal:** Optimizar el **Listado Operacional** como snapshot no editable de un ProductSheet usado por un Programmer.

El proyecto cuenta con **7 modelos relacionados**, pero el flujo crítico es:

```
ProductSheet (plantilla editable)
  └── ProductSheetOperation (operaciones editables de la plantilla)
      └── [snapshot al crear] 
          └── Programmer (orden de producción)
              └── ProductionOrderOperation (snapshot CONGELADO de operaciones - NO EDITABLE)
```

**Capas de dominio:**
1. **Catálogo/Maestro:** `Operation`, `OperationSection`, `Machine`
2. **Plantilla de Producto:** `ProductSheetOperation` (editable, con alias `ProductOperationList`)
3. **Órdenes de Producción:** `Programmer` (orden) + `ProductionOrderOperation` (snapshot read-only)
4. **Auditoría:** `OperationAuditLog`, `ProductSheetOperationHistory`

**Problema Core:** El Listado Operacional (ProductionOrderOperation) no está optimizado para:
- Visualización clara como snapshot no editable
- Trazabilidad completa vs ProductSheet original
- Integridad de datos congelados
- Performance en listados grandes

Se proponen optimizaciones concretas enfocadas en este flujo.

## 📊 Análisis Detallado por Modelo

### 1. **Operation** (`app/Models/ProductSheet/Operation.php`)

#### Funcionalidad
- **Maestro de operaciones:** Catálogo centralizado de todas las operaciones posibles.
- Cada operación tiene: `action` (tipo), `garment_part` (parte), `section`, `machine_id_reference`, `sam_base`.
- Incluye auditoría propia (`OperationAuditLog`).

#### Fortalezas
✅ Bien estructurado con relaciones claras  
✅ Validaciones de negocio encapsuladas (`scope`, accessors)  
✅ Soft deletes para trazabilidad  
✅ Generación automática de descripciones  

#### Problemas Identificados
❌ **Redundancia cruzada:** `ProductSheetOperation` duplica muchos campos (`action`, `garment_part`, etc.) innecesariamente.  
❌ **Accessors sin uso aparente:** `generated_description` y `normalized_name` generan complejidad pero no se usan en vistas.  
❌ **Scope `byNormalizedName`:** Usa `whereRaw` con concatenación; debería ser más simple.  
❌ **Múltiples FK a máquinas:** Aquí `machine_id_reference` y en `ProductSheetOperation` hay `machine_id`; confuso.  
❌ **Sin timestamps en `created_by`:** Dificulta auditoría de quién crea operaciones.  

#### Recomendaciones
| Acción | Prioridad | Descripción |
|--------|-----------|-------------|
| Eliminar `generated_description` y `normalized_name` si no se usan | Media | Simplificar el modelo, usar `name` directamente |
| Refactor scope `byNormalizedName` | Baja | Simplificar el SQL `whereRaw` |
| Asegurar uniqueness en `(action, garment_part, section_id)` | Alta | Prevenir duplicados accidentales |
| Agregar timestamps a `created_at` y `updated_by` | Media | Mejor trazabilidad |
| Documentar relación con OperationAuditLog | Baja | En el modelo o en servicio |

### 2. **Programmer** (`app/Models/ProductSheet/Programmer.php`)

#### Funcionalidad
- **Orden de Producción:** Representa una orden para producir unidades de un producto.
- Vinculada a `ProductSheet` (plantilla).
- Genera automáticamente snapshot de operaciones en `ProductionOrderOperation`.
- Puede ser **auto-generada** desde `ProductSheet` o **manual**.
- **IMPORTANTE:** En documentación se llama "ProductionOrder", pero el código usa el alias `Programmer`; es una decisión arquitectónica explícita (ver copilot-instructions.md).

#### Fortalezas
✅ Logging integrado en lifecycle (booted hooks)  
✅ Métodos semánticos (`isAutoGenerated()`, `isManual()`)  
✅ Distinción clara entre origen (`source` = 'auto' | 'manual')  
✅ Soft deletes para auditoría  

#### Problemas Identificados
❌ **Logging en modelo:** Los hooks `booted` registran eventos; mejor delegarlos a `ProgrammerService` o confiar en `AuditObserver` centralizado.  
❌ **Sin Enum para estados:** Campo `status` sin validación; debería ser Enum para type-safety.  
❌ **Relaciones incompletas:** Faltan `hasManyThrough` para acceso directo a máquinas/operaciones.  
❌ **`ecommerce_units` no tipado:** Array sin estructura; debería tener DTO o cast personalizado.  
❌ **Sin observador registrado:** No está en `AppServiceProvider::observe(AuditObserver::class)` de manera explícita.  

#### Recomendaciones
| Acción | Prioridad | Descripción |
|--------|-----------|-------------|
| Crear Enum `ProgrammerStatus` en `app/Enums/` | Alta | Reemplazar `status` string por enum: `pending`, `in_progress`, `completed`, `cancelled` |
| Remover booted hooks del modelo | Alta | Mover lógica a `ProgrammerService@handleCreated()`, `@handleUpdated()` |
| Registrar observador en `AppServiceProvider` | Media | Asegurar `Programmer::observe(AuditObserver::class)` con campos en `$auditIgnore` |
| Agregar relaciones `hasManyThrough` | Media | Acceso directo: `$programmer->machines()`, `$programmer->operations()` |
| Tipificar `ecommerce_units` con DTO | Media | Usar cast personalizado o DTO embebido

### 3. **ProductionOrderOperation** (`app/Models/ProductSheet/ProductionOrderOperation.php`) - SNAPSHOT CONGELADO

#### Funcionalidad
- **Snapshot no editable de operación:** Copia frozen de una operación en el contexto de una orden de producción.
- Generada automáticamente cuando se crea un Programmer (orden) a partir de un ProductSheet.
- **Rol crítico:** Es el Listado Operacional de la orden; Programmer lo consulta pero NO puede modificarlo.
- Almacena cálculos SAM (time) y factors específicos del momento de creación.
- Vinculado a `Programmer` (orden padre) y `Operation` (maestro para referencia).
- **Integridad:** Los cambios futuros en ProductSheet NO afectan este snapshot.

#### Fortalezas
✅ Modelo limpio y enfocado  
✅ Relaciones bidireccionales claras  
✅ Casts de tipos apropiados  
✅ Scope `byOrder` útil para queries  

#### Problemas Identificados
❌ **Sin auditoría:** No hereda `HasAuditLabel` ni tiene registro de cambios (crítico para snapshot).  
❌ **Campo `status` sin definición:** ¿Qué valores son válidos? Confuso en contexto read-only.  
❌ **Sin métodos de negocio:** Cálculos de SAM y progress no están encapsulados.  
❌ **Sin soft deletes:** Si un snapshot se borra, se pierden datos históricos de la orden.  
❌ **Sin relación a ProductSheetOperation original:** No hay trazabilidad a la operación fuente.  
❌ **Frontend:** Listados operacionales actuales no expresan claramente "read-only" en la UI.  

#### Recomendaciones
| Acción | Prioridad | Descripción |
|--------|-----------|-------------|
| Heredar `HasAuditLabel` y agregar `SoftDeletes` | Alta | Trazabilidad completa del snapshot; importante para auditoría |
| Crear Enum `ProductionOrderOperationStatus` | Alta | Estados: `pending`, `in_progress`, `paused`, `completed`, `cancelled` (para ejecución, no edición) |
| Agregar relación `productSheetOperation()` | Alta | FK a `ProductSheetOperation` original; permite comparar snapshot vs plantilla actual |
| Agregar métodos de negocio | Alta | `calculateProgress()`, `updateProgressOnly()` (progress es lo único que cambia), `isCompleted()` |
| Agregar `progressed_at` timestamp | Media | Registrar cuándo se actualizó SOLO el progreso |
| Marcar como inmutable en comentarios | Media | PHPDoc: "Este modelo es un snapshot congelado; NO editar operación, solo progress" |

### 4. **ProductSheetOperation** (`app/Models/ProductSheet/ProductSheetOperation.php`)

#### Funcionalidad
- **Operación de Plantilla:** Define las operaciones que debe tener un `ProductSheet` (plantilla de producto).
- Almacena parámetros SAM, factors, máquina, sección, tela base.
- Es plantilla generadora de `ProductionOrderOperation`.

#### Fortalezas
✅ Rica colección de fields y casts  
✅ Alias `ProductOperationList` para compatibilidad (deprecation clara)  
✅ Relaciones bien definidas  
✅ Métodos de cálculo SAM (`calculateSamTotalUnitario`, `calculateSamTotalOperacion`)  
✅ Soft deletes y auditoría  

#### Problemas Identificados
❌ **Tabla con nombre confuso:** `product_operation_lists` es antiguo; debería ser `product_sheet_operations`.  
❌ **Alias crear confusion:** `ProductOperationList` alias debería eliminarse completamente (ya deprecated).  
❌ **Campos de auditoría manual:** `created_by`, `updated_by` duplican `created_at`, `updated_at`; confuso.  
❌ **Cálculos sin persistencia:** `calculateSam*` recalcula cada vez; debería persistir o cacheable.  
❌ **Sin validación de secuencia:** `sequence` podría tener valores duplicados en una misma hoja.  
❌ **Campo `fabric_base_id` sin relación:** Comentario dice que referencia `fabric_bases` pero no hay relación.  

#### Recomendaciones
| Acción | Prioridad | Descripción |
|--------|-----------|-------------|
| Renombrar tabla a `product_sheet_operations` | Alta | Migración única; eliminar alias toda vez. |
| Eliminar completamente `ProductOperationList` | Alta | Usar `ProductSheetOperation` exclusivamente |
| Resolver campos `created_by` / `updated_by` | Alta | Usar `AuditLog` estándar del proyecto en lugar de duplicar |
| Crear relación `fabricBase()` explicit | Media | En lugar de comentario; agregar FK o usar cast |
| Agregar validación de uniqueness | Media | `unique:product_sheet_operations,product_sheet_id,sequence` |
| Persistir SAM calculados | Baja | Denormalizar si se usan a menudo; caso contrario, dejar como computed |

## 🎨 Análisis del Frontend - Enfoque: Listado Operacional (Read-Only)

### Contexto
El frontend debe mostrar el **Listado Operacional de una orden (Programmer)** de manera clara y eficiente:
- **Origen:** ProductSheetOperations (plantilla editable)
- **Snapshot:** ProductionOrderOperations (congelado en momento de creación de orden)
- **Uso:** Programmer visualiza (read-only) su listado operacional

El usuario NO puede editar operaciones de una orden ya creada; solo puede ver su progreso.

### Problemas Identificados

#### 1. **Archivos enormes (God Components)**

| Archivo | Líneas | Problemas |
|---------|--------|-----------|
| `Edit.vue` | 741 | Lógica de form + dialogo + normalización + http todo mezclado |
| `Create.vue` | 805 | Duplica funciones de normalización de Edit.vue |
| `Index.vue` | 723 | Lógica de filtros + tabla + paginación + permisos todo junto |

**Root cause:** Falta de separación de responsabilidades y composables especializados.

#### 2. **Código duplicado entre Create.vue y Edit.vue**

| Función | Líneas | Ubicación |
|---------|--------|-----------|
| `normalizeSeasonValue()` | ~20 | En ambos |
| `normalizeSeasonForApi()` | ~20 | En ambos |
| `normalizePriorityForApi()` | ~15 | En ambos (parcial) |
| `normalizeIsoDate()` | ~15 | Solo Edit.vue |
| Constantes MONTHS, PRIORITIES | 12 | En Create.vue (hardcoded) |

**Impacto:** Cambios deben hacerse en múltiples lugares; riesgo de inconsistencia.

#### 3. **Lógica de negocio sin encapsulación**

Funciones de normalización y validación están inline en componentes. Debería haber composables como:
- `useProgrammerForm()` - Validación y normalización de Programmer
- `useProgrammerNormalization()` - Conversión de fechas, temporadas, prioridades
- `useProgrammerFilters()` - Lógica de filtros en Index.vue

#### 4. **No hay DTOs separados para formularios**

El componente recibe `Programmer` directamente y lo modifica. No hay separación entre:
- **DTO de lectura** (desde API)
- **DTO de edición** (formulario editable)
- **DTO de envío** (payload normalizado para API)

Actualmente: `EditableProgrammer` es un hack manual en Edit.vue.

#### 5. **Manejo de alertas duplicado**

- `Index.vue` tiene su propia lógica: `alertMessage`, `alertType`, `showAlert`, `setAlert`, `clearAlert`
- `Edit.vue` usa `useAlertStack()`
- `Create.vue` usa `useAlertStack()`

**Problema:** Inconsistencia en la UI de alertas.

#### 6. **Cálculos de e-commerce sin test**

`EcommerceSizesDialog.vue` tiene lógica de parseo de tallas (`JSON.parse`, CSV, arrays) pero no tiene tests. Frágil ante datos malformados.

#### 7. **Constantes hardcodeadas en Frontend**

`Create.vue` define:
```typescript
const MONTHS = [
  { id: 1, name: 'ENERO' },
  // ... fallback cuando no viene del backend
];
```

**Problema:** Si el backend cambia, hay que actualizar dos lugares. Las constantes deberían venir del servidor.

#### 8. **Tipos sin validación en runtime**

Los tipos TypeScript (`Programmer`, `ProductSheet`) no tienen validación en runtime. Un payload malformado del backend rompe silenciosamente el frontend.

#### 9. **Selectores de opciones repetitivos**

Hay múltiples lugares donde se mapean arrays de opciones (`destinations`, `months`, `priorities`) a `SelectOption[]`. Hay un util `getProductSheetLabel()`, `getProductSheetValue()` pero faltan para opciones genéricas.

#### 10. **Paginación y filtros sin reactividad óptima**

`Index.vue` usa `watch()` con debounce manual; debería haber un composable `usePaginatedFilters()`.

### Backend Services - Patrón Establecido

**Archivo: `app/Services/ProductSheet/ProgrammerService.php`** (Nueva)

Ref. instrucciones: Lógica de negocio va en servicios, controllers delgados.

```php
namespace App\Services\ProductSheet;

use App\Models\ProductSheet\{Programmer, ProductionOrderOperation};

class ProgrammerService
{
    /**
     * Crear nuevo lote de programación
     */
    public function crearLote(array $datos): Programmer
    {
        $programmer = Programmer::create([
            'product_sheet_id' => $datos['product_sheet_id'],
            'temporada' => $datos['temporada'],
            'destino_id' => $datos['destino_id'],
            'source' => 'manual',
        ]);
        
        return $programmer;
    }
    
    /**
     * Obtener listado con filtros y paginación
     */
    public function obtenerListado(array $filtros = [])
    {
        $query = Programmer::query()->with('productSheet', 'destination');
        
        if ($filtros['temporada'] ?? false && $filtros['temporada'] !== 'todas') {
            $query->where('temporada', $filtros['temporada']);
        }
        // Más filtros...
        
        return $query->paginate($filtros['per_page'] ?? 10);
    }
}
```

**Beneficio:** Lógica centralizada, testeable, reutilizable.

```typescript
import { z } from 'zod'; // o valibot

export const ProgrammerFormSchema = z.object({
  product_sheet_id: z.number({ message: 'Referencia es obligatoria' }).min(1),
  season: z.string({ message: 'Temporada es obligatoria' }).min(1),
  destination_id: z.number({ message: 'Destino es obligatorio' }).min(1),
  units: z.number().nullable().optional(),
  priority: z.enum(['A', 'B', 'C', 'D']).nullable().optional(),
  estimated_delivery_date: z.string().datetime().nullable().optional(),
  ecommerce_units: z.record(z.number()).nullable().optional(),
});

export type ProgrammerFormValidated = z.infer<typeof ProgrammerFormSchema>;

export function validateProgrammerForm(data: unknown): { success: boolean; errors?: Record<string, string>; data?: ProgrammerFormValidated } {
  const result = ProgrammerFormSchema.safeParse(data);
  if (!result.success) {
    const errors = result.error.flatten().fieldErrors;
    return { success: false, errors: errors as Record<string, string> };
  }
  return { success: true, data: result.data };
}
```
**Beneficio:** Validación en runtime; mejor DX en desarrollo.
